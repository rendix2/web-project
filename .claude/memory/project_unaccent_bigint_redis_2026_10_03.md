Done 2026-10-03 in family-tree, alfred, rendix2-web-project (all uncommitted), test-first, suites green (family-tree Unit 53 / Functional 266, alfred Unit 71 / Functional 54 / Acceptance 69, web-project Unit 5 / Functional 34 / Acceptance 3, PHPStan clean in all three).

**unaccent:** migration `Version20261003180000` (all 3) = `CREATE EXTENSION IF NOT EXISTS unaccent` (trusted extension since PG13, DB owner can create it). The DQL `REGEXP()` function now compares `unaccent(CAST(x AS TEXT)) ~* unaccent(CAST(p AS TEXT))` (family-tree `Model/Doctrine/Functions/PostgresqlRegexp`, alfred `Database/Functions/Regexp` - MySQL branch untouched, web-project NEW `Database/Functions/Regexp`). family-tree also got a DQL `UNACCENT()` (`PostgresqlUnaccent`) used by `GlobalSearchControl`. Tests: `AccentInsensitiveSearchCest` (family-tree), `RegexpFunctionCest` (alfred), `GridFilterCest` (web-project). FOUND: in web-project the REGEXP function was never registered, so ANY admin grid text filter was a 500 (found by the new test). GOTCHA: Doctrine query/metadata caches (alfred nettrine FilesystemAdapter) keep old SQL / old entity mappings -> `make cached` after changing a DQL function or an entity attribute, otherwise tests lie (a BIGINT test passed on the old INTEGER entities until the cache was wiped).

**BIGINT ids:** entities `Types::INTEGER` id -> `Types::BIGINT` (PHP `int $id` stays: DBAL 4 returns int when it fits; web-project UserEntity/Mail/GeoIp already used `string $id` with BIGINT, untouched). Migration `Version20261003190000` (all 3) = PL/pgSQL DO block widening EVERY integer/smallint PK+FK column and integer sequence of the current schema to BIGINT, idempotent (no-op where already bigint), irreversible, PG-only (alfred/web-project on MySQL would need MODIFY statements - alfred's MySQL path is legacy). Test `BigIntIdentifiersCest` (Unit, all 3): entity metadata + information_schema/pg_sequences. family-tree dev DB (a pgloader import from MySQL) was ALREADY bigint everywhere (46 cols), a DB built only from migrations is integer -> verified on scratch databases (`CREATE DATABASE ft_scratch` + temporarily editing config/local.neon, then restored and dropped); same for web-project (`config/env/dev.neon`). alfred's SessionEntity (string id) is not numeric and was deleted anyway.

**family-tree dev DB migration drift:** 5 migrations were not recorded though the objects existed (`children` table); I registered `Version20250120203008` with `migrations:version --add` (table verified identical) and then ran the rest; a pg_dump taken before is in the session scratchpad. Dev DB has 1301 persons.

**web-project MySQL removed:** compose service + depends_on, `pdo_mysql` in both Dockerfiles and ci.yml, `type: mysql` in test.neon, AGENTS.md line, .gitignore entry. Left on disk: `.docker/mysql/` (109 MB data, untracked) - the user may delete it.

**alfred sessions -> Redis (contributte/redis ^0.6.2 + predis, like web-project):** `config/redis.neon` (included from config/common.neon and config/codeception/common.neon; connections `default` db0 with storage:false and `session` db1 sessions:true), parameter `redis.uri` default `tcp://alfred-redis`, compose service `alfred-redis`. Before this the DB `SessionHandler` was commented out in common.neon (production used PHP FILE sessions in /tmp, lost on every container restart/Watchtower redeploy) and only the Codeception config used the DB handler. Deleted: `SessionHandler`, `SessionEntity`, `Tables::SESSION`, `MigrationPresenter::runCleanSessions` (+ `cleanSessionsResult` JSON key), new migration `Version20261003200000` drops the `session` table. Test `RedisSessionCest` (session key in Redis db 1, TTL <= 14 d, login survives requests). **PROD MUST: add a Redis service to the alfred stack and set `redis: uri: tcp://<redis-host>` in production.neon BEFORE deploying - without Redis every request that starts a session errors.**
